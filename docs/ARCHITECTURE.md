# 架构与设计取舍

这份文档回答"为什么是这个形状"。具体命令看 `docs/*-COMMAND-REFERENCE.md`，
操作顺序看 `skills/*/SKILL.md`，安全边界看 `SECURITY.md`。

## 1. 一个工程，两个域，两个 CLI

```
rc   →  RestCloud iPaaS：查问题、改配置、改编排
dw   →  Apache Doris 数仓：查状态、刷物化视图、灰度换名、DDL 漂移
```

两个域**共用一个工程、一套 CI、一层通用原语**，但各自是**独立 CLI**（不是 `rc dw`）。
理由：它们是两个完全不同的系统，凭据、传输、命令面都不一样；
硬塞进一个命令族只会让帮助文本和参数解析互相打架。
但基础设施（错误码、脱敏、审计、快照、测试骨架）没有必要维护两份。

```
packages/core/src/         共享原语 + iPaaS 域
packages/core/src/dw/      数仓域（新增的域放这里，iPaaS 侧文件原地不动）
packages/cli/              rc 出口：只做参数解析 + 输出格式
packages/dw-cli/           dw 出口：同上
catalog/                   iPaaS 契约快照（端点/驱动/模板/错误映射）
skills/                    给 Agent 的 SOP（每个 CLI 一份）
docs/                      命令参考与契约
```

**分层的硬规矩**：能力在 `packages/core`，出口在 `packages/*-cli`。
`core` 里不做命令解析、不做输出格式；`cli` 里不写业务逻辑。
这样同一个能力可以被 CLI、验收脚本、单测三处复用，且换出口不用动能力。

**共享 vs 隔离**：

| 共享（core 通用层） | 隔离（各域自己的） |
|---|---|
| 错误码与退出码（`RcError`） | 配置根：`~/.rc` / `~/.dw` |
| 脱敏原语（`redact`） | 凭据文件与格式 |
| 目标主机白名单 | 传输方式（HTTP JSON vs FE REST / 外部命令） |
| 审计 sink、本地状态、快照 | 命令面 |
| 测试与 CI 骨架 | 文档与 SOP skill |

## 2. 为什么不要 MCP

Agent 通过 shell 调 CLI 已经足够：宿主（Claude Code / OpenCode / WorkBuddy）本来就有执行命令的能力。
再加一层 MCP server，等于多一份要同步维护的出口、多一套要单独覆盖的测试、
多一层模型与真实行为之间的转述——而收益只是"少拼一次命令行"。

**收敛到两个面：CLI（机器接口）+ skill（操作手册）。**
skill 负责把"什么时候用哪条命令、失败先看什么、什么绝对不能做"喂给模型，
这部分知识放在 Markdown 里比放在工具描述里更容易维护、更容易被人读懂。

## 3. 零运行时依赖

运行时**不引入任何第三方包**，只用 Node 22 内置能力：

- **用 Node 22 的 TypeScript strip-types 直接跑 `.ts`**，不需要构建步骤，
  也就没有"构建产物与源码不一致"这一类问题。
- **数仓走 FE 的 HTTP REST 端点**（`/api/query/{catalog}/{db}`），用原生 `fetch`。
  走 MySQL 协议就要引 `mysql2`，为了一个查询能力背一个依赖不值得。
  需要别的路径时用 `transport=cmd` 把 SQL 交给外部命令（argv 直传，不经 shell）。
- **SSH 隧道自研**：官方 CLI 只提供 SOCKS5，而我们要的是"配置里声明一下就能用"的本地转发。

代价是踩了一些协议细节（请求体必须是 JSON、响应是位置式 `result_set` 等），
这些都在 `docs/DW-COMMAND-REFERENCE.md` 里记着，不是猜出来的。

## 4. 安全模型

四条默认值贯穿全部命令，细节见 `SECURITY.md`：

1. **只读默认**：查询走只读闸门（单条 `SELECT/WITH/SHOW/EXPLAIN/DESC`，拒多语句）。
2. **写操作默认 dry-run**：必须显式 `--apply`。
3. **生产默认只读**：`RC_PROFILE=prod` / `DW_PROFILE=prod` 时写被拒，
   要放开必须显式设允许开关。这个判断**只在一个地方做**，不散落在各命令里。
4. **输出默认脱敏**：结果列、DDL 连接属性、host；`--raw` / `--reveal-host` 才回原值。

凭据只从环境变量 / 密钥管理 / 权限 0600 的独立凭据文件读，**不进 argv、不进日志、不进审计**。

## 5. 把踩坑固化成可执行断言

这个项目最有价值的部分不是"能跑命令"，而是**把反复踩过的坑变成会自动报的检查**。

- `rc flow validate` / `rc review flow`：平台侧 `checkerror` 偏松，本地是唯一兜底。
- `dw mv lint`：13 类线上踩过的建表/换名坑（库名限定、`STARTS` 过期、DECIMAL 除法提升、
  BUILD 方式被带过去、分区 MTMV 的 UNION / CTE 锚点 / VIEW / 自连接限制…）。
- `dw mv drift`：仓库定义 ↔ 线上 `SHOW CREATE`，先抹平注释、限定名、空白、自动补的属性再比，
  **报出来的都是真差异**。
- `dw mv phases`：按**实测耗时**判撞车，而不是按相位硬报。
- `dw mv refresh-mode`：直接读 `tasks()` 的 `RefreshMode` 判断分区 MV 的增量是否退化成了全量。

原则：**能变成断言的就不写成文档**。文档会被跳过，断言不会。

## 6. 开源与脱敏

仓库**不含**任何客户域名、IP、密码、token、逻辑库名、业务表名/MV 名。

- **能力通用、清单外部化**：`core` 里只有通用操作；环境、库、MV 清单一律来自配置或运行时发现，
  代码零硬编码。
- **业务词表从仓库外读**：内部表名/库名本身就是敏感面，所以它们进 CI secret 或本地文件，
  **不进仓库**。扫描器的通用特征写在代码里，具体词表外部注入。
- **扫描覆盖三个范围**：可发布文件（含未跟踪未忽略的）、git 历史、以及任意目录（`--dir`）。
  只扫已跟踪文件是不够的——新写的文件在 `git add` 之前既没进版本库也没被扫过。

## 7. 不做的事

不提供 MCP server；不新增 Web UI / 控制台 / 交互式 TUI；
不新增审批工单、许可分层、权限 IaC、团队协作；
不引入运行时依赖；不硬编码环境地址 / 库名 / 凭据；
**不把业务对账口径做成通用命令**——那是配置与配方的事，属于使用方的领域知识，不是工具的能力。
